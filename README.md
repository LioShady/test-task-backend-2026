# Ночная синхронизация CRM → Postgres

Точка входа — `collect_leads_customers(is_full=True)` в `main.py`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.

##
Старался сохранить минимализм исходного репозитория, оптимизировать код, не вводя новой логики.
Из этого вытекают компромиссы, например, в продакшене миграции стоит
реализовывать автоматизированно через alembic, константы вводить через конфиг и .env и т.д., 
но я осознанно опустил задачи, не относящиеся напрямую к оптимизации высоконагруженного приложения

## Что было дорого

Старая схема хранила всё в четырёх JSONB-массивах одной строки
`abstract_customer`, код создавал по коммиту в базу данных на каждую сущность:

- ~150–250 тыс. round-trip к Postgres на прогон:
  на каждого покупателя — 1–2 `SELECT` по `@>` (без индекса, seq scan)
  + `INSERT`/`UPDATE` + `commit`;
  на каждую сделку — то же плюс до 3 `commit` в ветке слияния.
- Десятки тысяч транзакций, commit на каждую сущность.
- Финальная чистка — `DELETE ... NOT IN (сотни тысяч ключей)` +
  `SELECT *` всей таблицы + `commit` внутри цикла по полям каждого покупателя.
- Память — `ids_map` на все сущности + полное чтение таблицы в фазе удаления,
  т.е. O(N) от объёма выгрузки.
- Логические баги: `jsonb_set` с индексом `len+1` (новый элемент не добавлялся),
  слияние в `lead_action` не срабатывало там, где должно, `except` без `rollback`
  «отравлял» сессию, `name = None` ронял фильтр «удалить».


## Что изменено

### Схема: JSONB-массивы были переписаны под нормализованные таблицы

### Загрузка: батчи + bulk `UPSERT`

`BATCH_SIZE = 2000`, на батч:

- 1–2 `SELECT ... WHERE id = ANY(:ids)` / `login = ANY(:logins)` — по индексам;
- 1 `INSERT ... ON CONFLICT DO UPDATE` на таблицу;
- 1 `UPDATE ... SET synced_at = :run_start WHERE id = ANY(:ids)` на таблицу;
- **один `commit` на батч**, а не на сущность.

Итого на 20k + 50k — **~400–500 запросов и ~40 транзакций** вместо
~150–250 тыс. запросов и десятков тысяч транзакций.

### Удаление: `synced_at` вместо `ids_map`

У каждой сущности есть `synced_at` — время старта прогона, в котором она была
в выгрузке. Фаза удаления:

- `DELETE ... WHERE synced_at < :run_start` по каждой таблице (по индексу);
- `DELETE ... WHERE lower(name) LIKE '%удалить%'`;

Избавился от чтения всей таблицы в память

### Оценка на заявленных объёмах

- Память: O(BATCH_SIZE) сущностей в буфере + один ответ API на страницу;
  не зависит от N. Старый код держал O(N) (`ids_map` + полное чтение таблицы).
- Запросы к Postgres: ~400–500
- Транзакции: ~40 (10 батчей покупателей + 25 батчей сделок + чистка).


## Миграция

Весьма тяжелая, хоть и одноразовая процедура миграции базы данных.

Скрипт `migrate_jsonb_to_tables.py`: переименование/перенос данных
из старой `abstract_customer` (JSONB-массивы) в новые таблицы, сдвиг sequence
`abstract_customer.id`, `DROP COLUMN` старых JSONB-полей. Всё одной транзакцией,
идемпотентно.

```bash
DATABASE_URL=postgresql+psycopg2://user:pass@host/db python migrate_jsonb_to_tables.py
```
